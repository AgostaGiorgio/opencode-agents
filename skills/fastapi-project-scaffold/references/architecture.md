# Architecture & conventions

Deep detail behind `fastapi-project-scaffold`. Read when bootstrapping, when
deciding how to grow the skeleton, or when verifying the generated project.

## Directory tree

```
<project>/
├── pyproject.toml              # Poetry: deps + version
├── poetry.toml                 # [virtualenvs] create = false
├── poetry.lock                 # generated by `poetry install`
├── Dockerfile
├── .dockerignore
├── .gitignore
├── .env                        # real secrets (never committed)
├── .env.example                # template, committed
├── config.yaml                 # optional YAML override (usually empty)
├── yoyo.ini                    # yoyo-migrations config
├── AGENTS.md                   # short guide for coding agents
├── README.md
├── migrations/
│   └── 0001_initial_schema.sql # `items` example table
└── src/                        # no __init__.py (namespace package)
    ├── main.py                 # FastAPI app + Container.wire + include_router
    ├── di.py                   # dependency-injector graph
    ├── config/
    │   └── app_config.py       # pydantic-settings + YAML
    ├── clients/
    │   └── postgres_client.py  # async engine/session factory wrapper
    ├── db/
    │   └── models/             # Pydantic models mirroring the SQL schema
    │       └── item.py
    ├── repositories/           # data access (raw SQL)
    │   ├── queries.py          # text(...) statements, referenced as q.NAME
    │   └── items.py
    ├── services/               # business logic
    │   └── items.py
    └── routers/                # FastAPI endpoints
        └── router.py
```

## Layer responsibilities

| Layer | Knows about | Must not |
| --- | --- | --- |
| `queries.py` | SQL text and `text()` objects | application objects |
| repository | `PostgresClient`, `queries`, Pydantic models | business rules, HTTP |
| service | repositories, business rules | SQL, sessions, `PostgresClient` |
| router | service, request/response models | SQL, repositories, sessions |
| `di.py` | wiring only | any logic |
| `app_config` | settings + connection URI | engine/session creation |
| `db/models` | Pydantic shapes mirroring tables/views | ORM/`DeclarativeBase` |

Call direction is one-way: router -> service -> repository -> client -> DB.

## Request lifecycle (example: `POST /api/v1/items`)

1. FastAPI validates the body into `ItemCreate` (Pydantic) -> 422 on bad input.
2. `@inject` + `Depends(Provide[Container.item_service])` resolves the service
   from the DI container (Factory -> a fresh instance per request).
3. The service calls `repository.create_item(...)`; the repository opens a session
   from the shared `PostgresClient` and executes `q.NEW_ITEM` inside a transaction.
4. The repository builds `Item(**row)` from the `RETURNING` mapping.
5. The router returns the model (serialized via `response_model`) or raises
   `HTTPException` when the repository returned `None`/`False`.

## DI wiring

`src/di.py`:

```python
class Container(containers.DeclarativeContainer):
    postgres_client = providers.Singleton(PostgresClient, db_url=app_config.postgresql_connection_uri)
    item_repository = providers.Factory(ItemRepository, postgres_client=postgres_client)
    item_service = providers.Factory(ItemService, item_repository=item_repository)
```

- **Singleton** for the client: one engine/session factory per app.
- **Factory** for repositories/services: a fresh instance per resolution.
- In `main.py`: `container = Container(); container.wire(modules=[router])`.
  `wire` patches the `Provide[...]` markers in the listed modules.
- When you split routers into modules, list **every** router module in
  `container.wire(modules=[...])`, not just the package.

## Single router vs multi-router

Default (scaffold): one `src/routers/router.py` exposing all endpoints, included
with a global prefix:

```python
app.include_router(router.api_router, prefix="/api/v1")
```

For larger APIs (MTrack style), one module per resource and per-resource prefix:

```python
from src.routers import items, users
container.wire(modules=[items, users])
app.include_router(items.api_router, prefix="/api/v1/items", tags=["items"])
app.include_router(users.api_router, prefix="/api/v1/users", tags=["users"])
```

Each module still defines its own `api_router = APIRouter()` and uses the same
`@inject` pattern.

## Configuration

`src/config/app_config.py` uses `pydantic-settings` (`BaseSettings`) reading `.env`,
then `AppConfig.load_from_yaml()` merges the optional `config.yaml` and exposes the
module-level `app_config` singleton. The DSN is a computed property:

```
postgresql+asyncpg://<user>:<password>@<host>:<port>/<database>
```

- Keep `extra = "ignore"` so unknown env vars (e.g. Docker/K8s) don't break startup.
- `config.yaml` may be empty; `yaml.safe_load` returning `None` is handled.

## Version handling

```python
_pyproject = Path(__file__).resolve().parent.parent / "pyproject.toml"
APP_VERSION = tomli.loads(_pyproject.read_text())["tool"]["poetry"]["version"]
```

The version lives **only** in `pyproject.toml`. Keep that table present; bumping
the version there is enough for FastAPI's `/docs` and (if enabled) Orbit.

## Database & migrations

- Schema is defined by **raw SQL** migration files in `migrations/`, applied with
  `yoyo apply`. Use sequential `NNNN_snake_case_description.sql` names.
- For writing migrations and mirroring them in `src/db/models/`, follow the
  `yoyo-sql-migrations` skill.
- At runtime the app uses **asyncpg**; yoyo uses **psycopg2** — keep both
  (`psycopg2-binary` + `yoyo-migrations` are dev dependencies).

## Verification checklist

Run from the project root after generation:

```sh
python -m compileall -q src
python -c "import src.main"                                          # app imports & wires
python -c "from src.di import Container; Container().item_service()"  # DI graph resolves
python -c "from src.main import app; print(len(app.routes))"          # routes registered
python -c "from src.main import APP_VERSION; print(APP_VERSION)"      # version read
```

`import src.main` needs a readable `.env` (or `config.yaml`) with the
`POSTGRESQL_*` values, but **not** a live database: `create_async_engine` is lazy.

With a reachable database:

```sh
yoyo apply --database <db_url> ./migrations
poetry run python src/main.py
curl -s localhost:8080/api/v1/items
curl -s -X POST localhost:8080/api/v1/items -H 'Content-Type: application/json' \
     -d '{"name": "hello", "description": "world"}'
```

## Docker

```sh
docker buildx build --platform linux/amd64 -t registry/<name>_be:0.1.0 .
```

The image installs Poetry, runs `poetry install`, and starts
`uvicorn src.main:app --port <port> --host 0.0.0.0`. When deploying into a
monorepo with other services, remember `VITE_API_BASE_URL`-style config is a
frontend concern and not part of this backend scaffold.
